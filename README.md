# 사장님도 퇴근합니다

자영업 사장님들이 가게 운영 경험과 고민을 나누는 커뮤니티 프로젝트입니다.

## 프로젝트 진행 현황

- **완료:** 1~10단계
- **현재 보완:** 관리자 목록 페이지네이션 + 서버 전체검색 RPC 연결
- **다음 단계:** 11단계 — 관리자 보안
- **작업 원칙:** 실제 코드와 Supabase 동작을 확인한 뒤 한 단계씩 진행합니다. 기존 기능과 디자인을 불필요하게 깨뜨리지 않고, 구현 후 실제 사용자 테스트를 거쳐 완료 처리합니다.

## 1. 실행

```bat
cd D:\sajangnim-community
git pull origin main
py -m http.server 3000
```

브라우저: **http://localhost:3000**

수정 후에는 `git pull origin main` 후 브라우저에서 `Ctrl + F5`로 강력 새로고침합니다.

> Git 충돌이 발생하면 임의로 `git reset --hard`를 실행하지 말고 `git status`와 오류 메시지를 먼저 확인합니다.

## 3. 관리자 시스템 — 10단계 완료

관리자 화면은 `profiles.role`이 `ADMIN` 또는 `MODERATOR`이고 `profiles.status`가 `ACTIVE`인 사용자에게 표시됩니다.

현재 구현된 관리자 기능:

- 관리자 대시보드
- 신고 관리
- 게시글 관리
- 댓글 관리
- 회원 목록 및 회원 상세
- 관리자 통합검색
- 신고/게시글/댓글 상태 한글화 및 색상 배지
- 회원 역할/상태 한글화
- 신고 대상 게시글/댓글 원문 확인
- 게시글 상세에서 즉시 숨김·삭제·복구
- 댓글 상세에서 즉시 숨김·삭제·복구
- 숨김/삭제 댓글 관리자 전용 조회
- 검색어 빨간색 강조
- 검색 결과에서 원문 위치로 바로 이동

### 관리자 목록 페이지네이션

신고관리, 게시글관리, 댓글관리는 **DB 전체 기록을 100건 단위로 페이지 이동**하도록 보완했습니다.

- 한 화면에 최대 100건 렌더링
- `이전 100건 / 다음 100건` 이동
- 전체 건수 및 현재 페이지 표시
- 신고: 전체 / 접수중 / 처리완료 / 기각 필터
- 게시글·댓글: 전체 / 공개 / 숨김 / 삭제 필터
- 처리완료/기각된 신고도 기록에서 자동 삭제되지 않음

페이지네이션은 Supabase 전체 데이터를 브라우저에 한 번에 내려받지 않고, 필요한 페이지 100건만 서버에서 조회합니다.

### 관리자 통합검색

기존의 최근 N건을 브라우저로 내려받아 찾는 방식 대신 **Supabase 서버에서 검색어 조건으로 전체 데이터 검색**하도록 보완했습니다.

검색 범위:

- 신고 사유/상세 및 신고 대상 내용
- 게시글 제목/본문/카테고리/업종
- 댓글 내용
- 회원 닉네임/업종/소개/ID

검색 결과는 분류별 최대 100건만 화면에 표시하지만, 검색 대상 자체는 최근 500건 같은 고정 범위가 아니라 DB 전체입니다.

## 4. 관리자 화면 한글 상태

| 원본 값 | 관리자 화면 표시 |
|---|---|
| `ACTIVE` | 공개 / 정상 |
| `HIDDEN` | 숨김 |
| `DELETED` | 삭제 |
| `PENDING` | 접수중 |
| `REJECTED` | 기각 |
| `RESOLVED` | 처리완료 |
| `USER` | 일반회원 |
| `ADMIN` | 관리자 |
| `MODERATOR` | 운영자 |

## 5. 관리자 전용 Supabase RPC

기존 함수:

- `admin_get_report_target`
- `admin_set_report_target_status`
- `admin_list_comments`
- `admin_list_post_comments`

페이지네이션/전체검색용 신규 함수:

- `admin_page_reports`
- `admin_page_posts`
- `admin_page_comments`
- `admin_unified_search`

신규 함수 SQL은 저장소의 `supabase-admin-pagination-search.sql`에 있습니다. Supabase SQL Editor에서 이 파일 전체 내용을 실행해야 새 페이지네이션/전체검색 기능이 활성화됩니다.

모든 신규 RPC는 `SECURITY DEFINER`를 사용하되 함수 내부에서 반드시 다음 조건을 검사합니다.

- `auth.uid()`와 일치하는 프로필
- `role IN ('ADMIN','MODERATOR')`
- `status = 'ACTIVE'`

SQL이 아직 적용되지 않은 환경에서는 프런트 보완 코드가 기존 관리자 목록/검색 기능으로 자동 복귀하도록 구성했습니다.

## 6. 보안 주의사항

- Supabase anon/publishable 키는 브라우저용 공개 키입니다.
- 실제 데이터 보호는 반드시 RLS와 서버 측 권한 검증으로 처리해야 합니다.
- `service_role` 키, OAuth client secret, 비밀번호 등 비밀정보를 GitHub나 `config.js`에 저장하면 안 됩니다.
- 관리자 메뉴가 화면에 보이지 않는 것만으로 보안이 확보되는 것은 아닙니다.
- 관리자용 RPC는 반드시 내부에서 관리자 역할과 계정 상태를 검증해야 합니다.
- RLS 오류가 발생해도 RLS를 끄거나 전체 공개 정책을 추가하지 않습니다.

## 7. 다음 단계 — 11단계 관리자 보안

다음 작업에서는 기능 추가보다 현재 관리자 기능의 권한 경계 검증을 우선합니다.

1. `profiles.role / status`를 일반 사용자가 수정할 수 없는지 확인
2. 관리자 전용 RPC마다 `auth.uid()` 기반 관리자 검증 확인
3. 일반 사용자가 관리자 RPC를 직접 호출했을 때 차단되는지 테스트
4. `posts`, `comments`, `reports`, `profiles` RLS 정책 점검
5. 브라우저 직접 REST 요청으로 관리자 동작을 우회할 수 없는지 확인
6. 관리자 상태 변경 기록 또는 감사 로그 필요 여부 검토
7. 회원 경고 기능을 추가할 경우 별도 경고 이력 테이블과 관리자 전용 처리 방식 설계
8. 회원 강제탈퇴와 마이페이지 회원탈퇴 정책 및 서버 측 Auth 삭제 방식 설계
